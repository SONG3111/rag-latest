## 0. 三十秒版本（面试官的第一问）

> "CRUD-RAG 那轮证明了'找得到'，这轮专测'排得准'。我们用 C-MTEB 榜单
> 里 Reranking 任务的标准数据集 T2Reranking（T2Ranking，arXiv 2304.03679）
> 的 dev 集：500 道真实用户查询，每道自带官方候选池（正例 + 抽样负例，
> 中位 15 条、最多 78 条）——这正是重排在生产里干的活：把召回池重排，
> 而不是全库重排。四种排序器在**同一批池子**上对拍：BM25、bge-m3 向量、
> RRF 融合、bge-reranker-v2-m3 交叉编码器，指标用榜单同款
> MAP + NDCG@10 + MRR@10 + Recall@10。结论：融合一致优于任一单腿；
> 重排 MAP/NDCG/MRR 三项全场最高，但我们抓到一个值得写进决策的细节——
> 重排的 Recall@10 略低于融合（0.7875 vs 0.7949），它是拿召回广度换
> top-1 精度的，这决定了它应该放在管线末端而不是替代融合。"

## 1. 测评集构成（重点）

### 1.1 为什么是 T2Reranking

- **身份**：C-MTEB（中文 MTEB）Reranking 榜单背后的标准任务，源自
  T2Ranking（arXiv:2304.03679）——大规模中文搜索排序数据集；
- **协议**：MTEB 官方把它实现为 `AbsTaskRetrieval`：每条查询自带候选池，
  主指标 **MAP（map_at_1000）**，同时报 NDCG@10 / MRR@10。我们逐条对齐：
  官方候选池从 dev parquet 的 positive/negative 列表**逐条重建**（文本
  规范化后精确匹配到 pid，8,229 个池位置 **0 条未匹配**），池结构固化在
  `tests/datasets/cmteb_reranking/pools.jsonl` 入库可查；
- **规模**：500 道查询（官方 dev 采样子集）、8,208 段落（全体候选池并集）、
  池大小 min/p50/max = 1/15/78。

### 1.2 标注

每条查询的 `relevant_pids` 即其池内全部正相关段落（min 1 / p50 7 / max 29），
二值相关。**重建验证**：官方 positive 列表与 `relevant_pids` 逐条一致，
确认池重建无损。

## 2. 测试方法（重点）

### 2.1 同池对拍：只让"排序器"动

四种模式排序**同一个官方候选池**，池子固定、正例固定，指标差异全部来自
排序器本身：

| 模式 | 排序依据 | 对应生产环节 |
| --- | --- | --- |
| bm25 | jieba+bigram Okapi BM25（生产 `BM25Index`） | 稀疏召回腿 |
| dense | bge-m3 余弦（生产嵌入模型，512 token 截断） | 稠密召回腿 |
| rrf | 双腿排名 RRF 融合（dense 1.0 / bm25 0.8，k=60） | 生产融合层 |
| rerank | bge-reranker-v2-m3 交叉编码器逐对打分（生产重排器） | 生产重排层 |

> **512 截断的三个理由**：bge-m3 官方检索指引 ≤512；生产子块预算 512；
> 生产重排器 `max_length=512`。T2Ranking 段落 p90 达 1,780 字符（≈2,500+
> token），截断让稠密腿与重排器"看到同样多的文本"，对比才公平——顺带
> 把 CPU 推理时间从"不可行"降到 62 分钟（这里有个真实的工程坑：langchain
> 改过属性名，`client` 变 `_client`，截断曾被静默跳过，速率差 10 倍，
> 已加显式报错防回归）。

### 2.2 指标（榜单同口径）

| 指标 | 通俗含义 |
| --- | --- |
| MAP | 全池平均精度均值——"正相关段落整体排得靠不靠前"，榜单主指标 |
| NDCG@10 | 前 10 名的位置加权命中率——头部排得准不准 |
| MRR@10 | 第一条正相关出现位置的倒数——"多快见到第一个对的" |
| Recall@10 | 前 10 名覆盖多少比例的正相关——广度 |

### 2.3 附加测量：候选生成召回

官方池是"给定池"，生产里池要靠自己召回。补充测量：BM25 top-30 / dense
top-30 / 两者并集各能抓住多少正相关——这是 `rerank_candidates` 取值的
直接依据。

## 3. 核心数据

500 题均值：

| 模式 | MAP | NDCG@10 | MRR@10 | Recall@10 |
| --- | --- | --- | --- | --- |
| bm25 | 0.6497 | 0.7065 | 0.7582 | 0.7736 |
| dense | 0.6705 | 0.7302 | 0.7697 | 0.7896 |
| rrf | 0.6698 | 0.7313 | 0.7756 | **0.7949** |
| **rerank** | **0.6758** | **0.7338** | **0.7784** | 0.7875 |

候选生成召回（top-30 内命中的正相关比例）：bm25 99.37% / dense 99.45% /
**并集 99.65%**。

四个读数：

1. **融合 > 任一单腿**（MRR/R@10 最高，NDCG 持平 dense、MAP 微低）：
   BM25 与向量的错误模式不同，RRF 取并集排序稳定占优——生产"双腿 +
   融合"的设计被 500 题独立验证；
2. **重排三项精度指标全场最高**：MAP +0.53pt、NDCG@10 +0.25pt、
   MRR@10 +0.28pt（vs rrf）。与 C-MTEB 榜单上交叉编码器对双塔的典型
   领先幅度一致；
3. **重排的 Recall@10 反而低于 rrf**（0.7875 vs 0.7949）：交叉编码器把
   一部分"融合排进前十"的相关段压到了十名开外。它买来的是 top-1~3 的
   精度，卖掉的是尾部的广度——**这正是重排该待在管线末端、且
   `rerank_top_n=5` 只取头部的结构性理由**：生产读的是头部，尾部广度
   由融合层兜着；
4. **候选生成近乎无损**：双腿并集 top-30 抓住 99.65% 的正相关，单腿也
   有 99.4%——`rerank_candidates=20~30` 的现行取值有依据（CRUD 轮还
   验证了 50 不比 20 好，本地 CPU 延迟省 2.5 倍）。

## 4. 决策与落地

| 项 | 决定 | 依据 |
| --- | --- | --- |
| 双腿 + RRF 融合架构 | **保留** | 500 题上融合一致优于单腿 |
| 重排在融合之后、只取头部 | **保留** | 重排精度三项最高但 R@10 回吐，末端定位正确 |
| 嵌入 512 token 窗口 | **文档化** | 与生产子块预算、重排器截断对齐；脚本内显式校验防静默失效 |
| 换更大重排器/云端 gte-rerank | **观察** | 本地重排已带来稳定增益；云端配额受限（免费额度耗尽），且增益边际 |

## 5. 追问预演

**Q：你们的重排数字和 C-MTEB 榜单能对上吗？**
A：量级一致但不能逐位对——三个差异都写在方法里：我们用官方 dev 集的
500 题子集而非全量；池重建经 0 失配校验但文本规范化细节可能带来个位
数差异；嵌入式截断 512（榜单多数模型编码更短，方向上对我们更严）。
MAP 0.6758 落在榜单交叉编码器的典型区间内，**口径讲清楚比数字漂亮
重要**。

**Q：重排 R@10 掉了，生产会不会因此漏答案？**
A：生产的读法决定了这个 trade-off 是赚的：管线末端只取 top-5 交给模型
（`rerank_top_n=5`），尾部第 6~10 名本来就不进上下文；而 top-1~3 的
排序精度直接决定"模型第一眼看到的是不是对的"。广度由融合层负责——
各层干各自擅长的事，这正是分层检索的本意。

**Q：为什么不顺便测更大的重排器（bge-reranker-v2-large 等）？**
A：本轮目标是验证**现有生产配置**的每一层是否值得存在，以及和社区
标准答案对表；换模型是下一轮的事，且应该先在 CRUD-RAG（业务形态）
上过一遍，避免只在榜单题上挑模型。

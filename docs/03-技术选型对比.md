# 03 技术选型对比

本文回答两个问题：**为什么选它**、**什么场景下应该换成别的**。
每一节的结构统一为：结论 → 对比表 → 判断标准。

## 0. 一句话结论：什么场景选什么

| 你的场景 | 推荐配置 | 理由 |
|---|---|---|
| 只想看效果 / 没有 API key | `RERANKER_PROVIDER=noop` + 仅 BM25 | 零模型依赖，立刻能跑，代价是召回率下降 |
| 日常单机使用（本项目默认） | LLM 云端 + Embedding/Rerank 本地 | 隐私与成本平衡：语料不出机器，只有对话出网 |
| 完全离线 / 内网 | 全部本地（LLM 换 Ollama 或 vLLM） | 需要接受工具调用稳定性下降 |
| 语料是法条、合同、报表 | 保持混合检索 + 提高 `RETRIEVAL_BM25_TOP_K` | 精确 token（条款号、金额）比语义更重要 |
| 语料是客服问答、散文 | 提高向量权重、降低 BM25 权重 | 语义泛化比字面匹配更重要 |
| 多用户 / 团队共享 | 换 Postgres + Qdrant server + 对象存储 | SQLite 与嵌入式向量库是单进程独占 |
| 要接生产系统 | 加鉴权、审计强化、权限模型、异步任务队列 | 见 [04 落地与改进](04-落地与改进.md) |

## 1. Agent 框架：LangGraph vs 其他

| 方案 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| **LangGraph（本项目）** | 图即状态机，节点/边/状态显式；支持流式双通道（updates + messages）；循环可控 | 概念多，学习曲线陡 | 需要在"工具循环"里插入自定义节点（如审批、兜底） |
| LangChain `AgentExecutor` | 上手最快 | 控制流是黑盒，插入自定义分支要改源码；难以观测 | 一次性脚本、Demo |
| CrewAI / AutoGen | 多角色协作开箱即用 | 面向"多 Agent 对话"，本项目是单 Agent + 工具；多引入一层不确定性 | 研究型多角色任务 |
| 自己写 while 循环 | 完全可控 | 流式、状态、消息归并、重试都要自己写（LangGraph 已经解决） | 极简场景 |

**为什么选 LangGraph**：这里的核心诉求不是"多智能体协作"，而是**在工具循环里插桩**——
写入要拦截、检索要兜底、空回复要纠正、token 要实时推给前端。
LangGraph 允许把这些做成独立节点与条件边，而不是塞进一个巨大的回调函数里。

**什么时候该换**：如果你的需求只是"问一句答一句"，没有工具、没有审批，
那么 LangGraph 是过度设计，直接调 SDK 更简单。

## 2. 工具协议：MCP vs 普通函数 vs HTTP/OpenAPI

| 方案 | 优势 | 劣势 |
|---|---|---|
| **MCP（本项目）** | 工具契约标准化（JSON Schema + 注解）；进程隔离；Server 可被其他客户端复用 | 多一层子进程与协议开销；调试要会看 stdio 日志 |
| 普通 Python 函数 | 最快、最好调试、类型直接可见 | 与宿主强耦合，工具定义与审批策略混在业务代码里 |
| OpenAPI / HTTP 服务 | 天然支持远程、多语言 | 需要起服务、管端口、考虑鉴权；本地文件操作反而变复杂 |

**为什么选 MCP**：

1. **注解就是审批策略**。`readOnlyHint` / `destructiveHint` 由协议承载，
   Agent 侧不需要维护一份"哪些工具危险"的硬编码清单；新增工具忘记标注时
   **默认按危险处理**（fail safe）。
2. **进程隔离**：文档解析崩了不会带走后端进程；沙箱根通过环境变量注入，
   工具本身对"工作区"没有概念。
3. **简历/工程价值**：这是当前工具生态的标准协议，独立 Server 可以脱离本项目单独复用。

**什么时候该换**：如果工具只在单个进程内使用、且不需要被别的客户端复用，
普通函数更省事。MCP 的收益来自"契约标准化 + 隔离"，规模小时是纯成本。

## 3. 审批放在哪一层

| 位置 | 做法 | 问题 |
|---|---|---|
| **Agent 层（本项目）** | MCP Server 只执行；后端在"决定调用"和"真正调用"之间拦一层，落库成提案 | 需要后端有数据库与状态机 |
| MCP Server 内部 | 工具自己等确认 | Server 变成有状态，无法复用；确认逻辑要跨进程传递 |
| LangGraph `interrupt` | 用图的中断能力暂停 | 需要 checkpointer 与可恢复线程，进程重启后状态丢失，审计不落地 |

**为什么选 Agent 层**：审批记录必须是**持久、可审计、可还原**的。
放在 SQLite 里，"谁在什么时候同意了哪次修改、原值是什么、备份在哪"都能查；
而图状态在服务重启后就没了。

**什么时候该换**：如果允许"一次性批量变更、事后审计"，可以用 interrupt + 事中弹窗，
交互更顺滑；代价是审计证据变弱。

## 4. 检索策略

| 方案 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| **混合（向量 + BM25 + RRF + 重排，本项目）** | 精确 token 与语义泛化兼顾；有绝对分数可用于拒答 | 链路长，参数多，需要标定 | 中英混排的业务文档、表格 + 制度 |
| 纯向量 | 实现简单，语义泛化好 | 金额、编号、人名容易被"模糊"；没有可靠的拒答信号 | 散文、FAQ |
| 纯 BM25 | 快、零模型、可解释 | 换个说法就找不到（"报销咋整" vs "报销流程"） | 术语高度固定的语料 |
| Elasticsearch 全家桶 | 成熟、可水平扩展 | 部署重、中文分词要额外配置 | 已有 ES 基础设施 |

实测差距（同一评测集 36 题）：

| 配置 | Recall@5 | MRR | 拒答准确率 |
|---|---|---|---|
| 仅 BM25 | 0.8214 | 0.8036 | 0.2500 |
| + 向量 + 重排 | 0.8929 | 0.8571 | 1.0000 |
| + 改写 | 0.9286 | 0.9107 | 1.0000 |

两个转折点值得记住：

- **口语化提问**（6 题）：仅 BM25 命中 2/6 → 加向量 4/6 → 加改写 5/6。
- **多轮指代**（4 题）：仅 BM25 命中 3/4 → 加向量后 2/4（**变低**，因为阈值把
  无法解析的问题正确拦成"拒答"）→ 加改写回到 3/4。这个"先降后升"说明阈值与改写
  是配套的：没有改写时，报"没找到"比返回无关内容更正确。

**为什么 RRF 而不是分数归一化**：BM25 分数与余弦相似度不同量纲（前者可以 >10，
后者在 [0,1]），归一化需要假设分布，而 RRF 只用排序，天然鲁棒。

**什么时候该换**：
- 语料是纯散文、没有精确 token → 可以砍掉 BM25，链路更短；
- 语料是纯结构化数据（全是表格）→ 反过来应该提高 BM25 权重，甚至考虑
  text2sql 之类的方式；
- 已经有 ES → 直接用它做 BM25 + kNN，省一套 Qdrant。

## 5. 重排

| 方案 | 延迟 | 效果 | 成本 |
|---|---|---|---|
| **本地交叉编码器 bge-reranker-v2-m3（本项目）** | 20 个候选约 0.8s（CPU） | 好，且给出**绝对**相关性分数 | 一次性加载约 10s（已按配置缓存） |
| 云端重排（如 DashScope `gte-rerank`） | 网络往返 + 排队 | 好 | 按量计费，语料片段出网 |
| LLM 直接重排 | 数秒 | 好，可解释 | 贵，且分数不可比、不稳定 |
| 不重排 | 0 | 排序质量依赖召回 | 0 |

**为什么选本地**：除了隐私，更关键的是**它提供可用于拒答的绝对分数**。
RRF 融合分是相对的（永远有第一名），无法回答"这段到底相关吗"；
交叉编码器给的是"这两段文本相关吗"的绝对判断，阈值才有意义。

**什么时候该换**：候选数很多（>100）或要上 GPU 集群时，云端重排更划算；
离线场景则必须本地。切换只需改 `RERANKER_PROVIDER`。

## 6. Embedding：本地 vs 云端

| 维度 | 本地 bge-m3（本项目） | 云端 text-embedding-v3 |
|---|---|---|
| 数据出网 | 否 | **是（语料原文）** |
| 首次加载 | 数秒 | 无 |
| CPU 推理 | 可用（较慢） | 不占本地算力 |
| 维度 | 1024 | 1024（可配） |
| 成本 | 0 | 按 token 计费 |
| 多语言/长文本 | bge-m3 支持 8k 上下文、多语言 | 好，但受接口限制 |

**为什么默认本地**：这个项目处理的往往是内部制度、报销明细这类**不该外传**的文档。
把整个知识库的原文交给第三方换来的只是"不用装权重"，不值得。

**什么时候该换**：批量导入海量语料、机器没有足够内存/算力、或需要与云端检索共用同一空间时，
改 `EMBEDDING_PROVIDER=dashscope` 即可（记得同步 `EMBEDDING_DIMENSIONS` 并重建索引）。

## 7. 分块策略

| 方案 | 引用精度 | 上下文完整度 | 成本 |
|---|---|---|---|
| **父子分块（本项目）** | 高（精确到行/段） | 高（父块补齐） | 嵌入量 ≈ 子块数量（父块不嵌入） |
| 固定窗口（如 700 字 + 80 重叠） | 中（"第 3-8 段"） | 中 | 低 |
| 语义分块（按语义断点） | 中 | 中 | 需要额外模型或计算 |
| 整文件一个块 | 低 | 高（但噪声大） | 最省，但检索质量差 |

**为什么选父子**：答案既要"精确到哪一行"，又要"看得懂这一行"。
固定窗口做不到同时满足，而"把两种粒度都嵌入"会让索引成本翻倍。
父子结构只嵌入子块，父块作为上下文附件返回，是效果与成本折中的最优解。

**实测细节**：Excel 子块带表头（`第2行: 产品=A型, 区域=华东, 销售额=1000`），
所以模型看到的永远是有列名的数据；Word 子块是一段或一个表格行，父块是整节。

**什么时候该换**：语料是长文报告、章节很长时，可以改成"章节摘要 + 段落"的两级；
如果语料本身已经是结构化问答对（Q&A），直接按问答对分块更简单。

## 8. 向量库

| 方案 | 部署 | 多进程 | 过滤能力 | 适用 |
|---|---|---|---|---|
| **Qdrant local（本项目）** | 嵌入式，一个目录 | **不支持**（文件锁） | payload 过滤 | 单机、单进程 |
| Qdrant server | Docker 一条命令 | 支持 | 同左 | 多进程/多用户 |
| Chroma | 嵌入式 | 有限 | 基础 | Demo |
| FAISS | 纯库，需自己持久化 | 不支持 | 无 | 离线批处理 |
| pgvector | 跟随 Postgres | 支持 | SQL 全能力 | 已有 Postgres |

**为什么选 Qdrant local**：单机运行时零部署、支持 payload 过滤（按 workspace、file_id 过滤），
且每工作区一个 collection 让"删工作区"变成一次 `delete_collection`。

**什么时候该换**：
- 后端与评测脚本需要**同时**访问 → 现在会报 "Storage folder ... already accessed"
  （这条限制在本项目里真实遇到过）；
- 需要多用户/多实例 → 换 Qdrant server 或 pgvector。

## 9. 关系数据库

| 方案 | 优势 | 劣势 |
|---|---|---|
| **SQLite（本项目）** | 零部署、单文件、事务完备 | 单写者；并发写会锁 |
| Postgres | 并发、JSONB、pgvector、权限 | 需要部署与运维 |

**为什么选 SQLite**：项目是单用户本地运行，元数据量小（每工作区几百到几千行），
而 SQLite 的"一个文件就是全部状态"对本地工具是巨大优势（备份=复制文件）。

**什么时候该换**：多用户、多实例、或需要与外部系统共享数据时。
SQLAlchemy 已经做过抽象，换连接串 + 迁移即可。

## 10. 后端框架：FastAPI vs 其他

| 方案 | SSE 支持 | 类型/校验 | 生态 |
|---|---|---|---|
| **FastAPI（本项目）** | 原生 async + `sse-starlette` | Pydantic 自动校验与文档 | 与 LangChain / SQLAlchemy 同语言栈 |
| Flask | 需要额外扩展做流式 | 手写校验 | 轻 |
| Django | 重量级，DRF 对 SSE 不友好 | 强 ORM | 全功能但与 AI 生态割裂 |

**为什么选 FastAPI**：本项目重度依赖 async（SSE 流式、MCP 异步调用、模型流式），
FastAPI 的 async 与类型校验让接口层非常薄；`/docs` 自动生成的接口文档对交接很有用。

## 11. 前端：Vue 3 + Vite vs React/Next

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Vue 3 + Vite + Pinia（本项目）** | 上手快、单文件组件直观、Vite 冷启动快；Ant Design Vue 表格/表单开箱即用 | 生态规模小于 React |
| React + Next.js | 生态最大、SSR/路由成熟 | 对纯本地 SPA 来说 SSR 是负担；状态管理选择多反而耗时 |
| Svelte | 代码量最少 | 组件库生态弱，Ant Design 类库缺失 |

**为什么选 Vue**：本项目是**本地单页应用**，不需要 SSR/SEO；前端复杂度主要在
流式渲染与状态同步，Vue 的响应式心智负担更小。

**什么时候该换**：要发布成公开站点、需要 SEO 或服务端渲染，或团队已有 React 技术栈。

## 12. 流式传输：SSE vs WebSocket

| 方案 | 单向/双向 | 断线重连 | 复杂度 | 适用 |
|---|---|---|---|---|
| **SSE（本项目）** | 服务端→客户端单向 | 浏览器原生支持 | 低（普通 HTTP） | 流式生成、进度推送 |
| WebSocket | 双向 | 需要自己实现 | 需要连接管理、心跳 | 双向实时协作、多人编辑 |

**为什么选 SSE**：这里只有"服务端推、客户端收"，用户输入走普通 POST。
SSE 是纯 HTTP，穿过代理/开发服务器的成本最低（Vite 代理一条规则就够）。

**怎么选**：只有当客户端需要在流中途双向干预（多人同时编辑同一文档、实时协作光标）时
才值得上 WebSocket。像"停止生成"这种需求，SSE 下前端直接断开连接就够了
（本项目目前还没提供该按钮，属于 [04](04-落地与改进.md) 里的体验项）。

> 提醒：SSE 帧以 **CRLF** 结尾，前端不能用 `'\n\n'` 切分——这个坑在
> [02 端到端流程](02-端到端流程.md) 的失败手册里有详细说明。

## 13. 查询改写：LLM vs 规则 vs 不用

| 方案 | 效果 | 成本 | 风险 |
|---|---|---|---|
| **LLM 改写（本项目）** | 口语化与多轮指代都能处理 | 每次检索多一次模型调用（实测 4~8s） | 模型可能改错意图 |
| 同义词表 / 规则 | 快、可解释 | 覆盖率低，维护成本高 | — |
| HyDE / 多查询扩展 | 召回更高 | 多次生成 + 多次检索，延迟翻倍 | 复杂度高 |
| 不改写 | 0 | 多轮与口语场景明显掉分 | — |

**为什么选 LLM 改写 + 独立小模型**：改写是小转换任务，用便宜快速的模型即可，
不占用对话模型的延迟预算；并且**失败一定回退原查询**，最坏情况等价于"不改写"。

**为什么不做 HyDE / 多查询**：本项目语料是制度与表格，问题通常是"某个事实是多少"，
多查询带来的召回提升有限，而延迟与复杂度会被用户直接感知。

## 14. 拒答机制

| 方案 | 表现 | 代价 |
|---|---|---|
| **阈值过滤 + 提示词双保险（本项目）** | 拒答准确率实测 1.00 | 需要标定阈值 |
| 只用 LLM 判断"能不能回答" | 灵活 | 多一次调用，判断不稳定 |
| 不做 | 一定胡编 | 0 成本，但产品不可信 |

**阈值怎么来**：不是抄的，是扫出来的。`--sweep` 复用同一批检索结果只改过滤条件，
因此几乎不增加开销。0.02 是第一个把拒答做到 100% 的取值。

**什么时候该换**：语料换成另一批文档、或换重排模型后，**必须重新扫**。
阈值取决于被打分文本的长度：长段落正确命中可达 0.9，而本项目的短子块只有 0.05 量级。
照搬别人的阈值会静默损伤召回。

## 15. 提示词从哪来

| 方案 | 优势 | 劣势 |
|---|---|---|
| **迁移开源项目的成熟提示词（本项目）** | 结构经过验证（角色/任务/限制/示例/检查清单）；可追溯来源 | 需要人工适配到自己的场景与格式 |
| 自己写 | 完全贴合业务 | 容易漏掉关键约束（引用纪律、拒答边界） |
| 让模型生成提示词 | 快 | 缺乏原则，回归时无从对比 |

本项目迁移的四处（详见 `backend/app/agent/prompts.py` 顶部注释）：

- **LlamaIndex** `DEFAULT_TEXT_QA_PROMPT_TMPL` → "只能依据上下文，不用先验知识"；
- **RAGFlow** `sufficiency_check.md` → 证据不足要说清缺什么；
- **RAGFlow** `citation_prompt.md` → 引用纪律（引什么、不引什么、放哪、几个、不许编造）；
- **RAGFlow** `next_step.md` 的 `<verification_steps>` → 交付前自检清单；
- 改写提示词迁移自 **RAGFlow** `full_question_prompt.md`。

## 16. 部署方式

| 方案 | 适用 | 说明 |
|---|---|---|
| **本地脚本（开发默认）** | 单人开发 | `.venv312` + `npm run dev` |
| Docker Compose（已提供） | 演示/交付 | 注意本地模型目录需要挂载进容器，否则要切云端 embedding |
| 单机服务 + systemd | 长期运行 | 需要自己管进程与日志轮转 |
| K8s | 多实例 | 需要先解决 SQLite 与嵌入式 Qdrant 的单进程限制 |

**什么时候该换**：只有出现"多人使用 / 需要 7×24 / 需要横向扩容"时才值得上 K8s；
在那之前，把 [04 落地与改进](04-落地与改进.md) 里的 P0 项做完收益更大。

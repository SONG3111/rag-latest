# 04 落地与改进

这一篇回答："如果这不是简历项目，而是一个真要给团队用的系统，还差什么？"

## 一、现状定位

把系统放在"原型 → 内部工具 → 团队产品"的坐标上：

```
原型 ────────────▶ 内部工具 ────────────▶ 团队产品
        ▲
      现在在这里
```

**已经具备的"产品级"特征**（不只是 Demo）：

- 危险操作有审批闭环、有备份、可还原、有审计
- 拒答是设计目标之一（有负样本评测集，不是拍脑袋）
- 失败路径被明确处理（无 key、超时、MCP 崩溃、代理、schema 漂移、空回复）
- 全链路有回归测试与可复现的评测脚本

**还缺的**（决定它能否被第二个人使用）：

| 类别 | 现状 | 缺什么 |
|---|---|---|
| 身份 | 无账号 | 谁在用？谁能看哪个工作区？ |
| 并发 | 单进程独占 SQLite / Qdrant local | 多人同时用会互相锁 |
| 长任务 | 上传与重建索引同步阻塞 | 大文件会把请求挂住几分钟 |
| 模型韧性 | 单模型，报错就直接失败 | 额度用尽/限流时无降级 |
| 可观测 | 日志 + 落库 | 没有指标、没有 tracing、没有成本统计 |
| 数据治理 | 备份 50 份 + 单次还原 | 没有文件版本历史、回收站、保留策略 |
| 前端规模 | 一次取最近 200 条消息 | 长会话无分页/虚拟滚动 |
| 交付 | Docker Compose | 没有 CI、没有一键安装脚本、没有健康面板 |

下面按优先级给出改进项。

## 二、改进清单

### P0：影响"能不能用"的问题

**P0-1 长任务异步化（上传、重建索引）**

- 问题：`POST /files` 同步解析 + 嵌入，大文件或换模型重建时会挂住请求；
  前端只能转圈，没有进度。
- 方案：引入后台任务（先用 FastAPI `BackgroundTasks`，量大再上 RQ/Celery），
  状态写回 `document_files.status`（`pending / indexing / indexed / failed`），
  通过 SSE 或轮询推送进度。
- 涉及：`backend/app/api/routes.py`、`backend/app/services/files.py`、
  `frontend/src/components/WorkspaceSidebar.vue`
- 验收：上传 50MB 文件时接口 200ms 内返回；索引完成前文件状态可见；失败可重试。

**P0-2 上传安全加固**

- 问题：现在只校验后缀与大小。xlsx 可以塞宏、压缩炸弹；
  写入以 `=` 开头的字符串会被 Excel 当公式（CSV/公式注入）。
- 方案：
  1. 只接受 `openpyxl` / `python-docx` 能正常打开的文件，并限制解压后体积与条目数；
  2. `update_cells` 遇到以 `= + - @` 开头的字符串时，默认按**文本**写入（前置单引号），
     只有显式的 `set_formula` 才写公式；
  3. 拒绝含 VBA 的 `.xlsm`（或明确提示）。
- 涉及：`backend/app/services/files.py`、`mcp-office-server/src/mcp_office_server/excel_ops.py`
- 验收：构造一个 1000:1 压缩比的 xlsx，上传被拒且后端不 OOM；
  让 Agent 写入 `=1+1`，打开文件看到的是文本而不是公式（除非用 `set_formula`）。

**P0-3 模型降级与错误提示**

- 问题：模型额度用尽时，用户看到的是一大段供应商报错（本项目真遇到过
  `403 AllocationQuota.FreeTierOnly`）。
- 方案：配置主/备模型列表；主模型返回 4xx/5xx 或超时时切备用；
  把供应商错误翻译成人话（"模型额度不足，请在控制台充值或切换模型"）。
- 涉及：`backend/app/llm/providers.py`、`backend/app/agent/graph.py`、
  `backend/app/api/routes.py`（error 事件）
- 验收：把主模型名改成不存在的模型，系统自动使用备用模型并成功回答；
  两个都不可用时，界面显示可操作的中文提示。

**P0-4 并发与存储边界**

- 问题：SQLite 单写者；Qdrant local 被进程独占（后端运行时跑评测脚本会报
  "Storage folder ... already accessed"）。
- 方案：
  1. 明确文档化"同一时刻只有一个进程访问 data/"，并提供只读脚本模式；
  2. 需要并行时：Postgres（或至少 SQLite WAL + 串行写队列）+ Qdrant server。
- 涉及：`docker-compose.yml`、`backend/app/db.py`、`backend/app/retrieval/vector_store.py`
- 验收：后端运行时执行 `eval_retrieval.py` 不报锁错误（走只读连接或服务端向量库）。

### P1：把"能演示"提升为"敢长期用"

**P1-1 检索评测集扩充 + 回归门禁**

- 现状：36 题（18 库内 / 6 口语 / 8 负样本 / 4 多轮）。
- 目标：扩到 100+，覆盖多文件、跨文件比较、超大表格、Word 表格、日期与金额格式差异。
- 方案：`eval_retrieval.py` 支持按类别输出与阈值/权重扫描；把"Recall@5 不低于基线、
  拒答准确率不低于 0.95"写成可执行断言，接进 CI。
- 验收：任何一次改动如果让基线下降，CI 变红。

**P1-2 引用可点击定位**

- 现状：回答里有 `[制度.docx · 段落 2]`，右侧有引用面板，但点了不会跳到原文。
- 方案：引用卡片上提供"查看原文"，用已存的分块 `location` 打开文件预览并高亮对应行/段。
- 涉及：`frontend/src/components/InspectorPanel.vue`、`GET /files/{id}/download`
  （可扩展成 § 级定位）。
- 验收：点引用能定位到具体行，而不是只下载整个文件。

**P1-3 写入冲突的前端闭环**

- 现状：`WriteConflict`（文件被外部改动）会变成一条工具错误丢回模型。
- 方案：识别该错误码 → 自动重新读取 → 重新生成提案 → 在界面上提示"文件已被外部修改，
  已按最新内容重新生成提案"。
- 验收：手工在 Excel 里改一个值再确认旧提案，界面给出明确提示而不是静默失败。

**P1-4 批量确认与冲突合并**

- 现状：多个提案逐条确认；同一单元格被改两次会各生成一条提案。
- 方案：按文件聚合成"一批变更"，同一目标的提案按时间折叠（后写覆盖，确认时提示），
  支持"全部应用 / 全部拒绝"。
- 验收：一次让 Agent 改 20 行，界面是一次确认；同一单元格两次修改只出现最终值。

**P1-5 可观测性**

- 现状：日志 + 数据库审计；没有指标与 trace。
- 方案：结构化日志（JSON）、关键指标（检索耗时、候选数、阈值过滤数、工具调用次数、
  模型 token 与费用）、可选 OpenTelemetry 接入。
  每次检索的候选与分数落库，便于"这次为什么答错"的复盘。
- 验收：能回答"昨天那次答错，是召回没找到还是阈值卡掉了"。

**P1-6 成本与配额**

- 现状：没有 token 统计与预算控制。
- 方案：按工作区/会话统计 token；配置每日预算上限，超限后自动切换到"仅本地检索 +
  不调 LLM 改写"的降级模式。
- 验收：预算耗尽时系统仍可检索（BM25），并明确告知用户当前处于降级模式。

### P2：从"单人工具"到"团队产品"

| 项 | 内容 | 关键动作 |
|---|---|---|
| P2-1 身份与权限 | 登录 + 工作区成员 + 角色（只读/可写/可审批） | 引入认证中间件；`workspaces` 加 owner/成员表 |
| P2-2 多租户存储 | Postgres + 对象存储 + Qdrant server | 迁移脚本 + 连接串切换 |
| P2-3 文件版本历史 | 每次写入生成版本，可对比任意两版 | 复用备份机制，落 `file_versions` 表 |
| P2-4 增量索引 | 按 `checksum` 跳过未变文件；只重建变更文件 | `index_file` 前比对 checksum |
| P2-5 前端规模化 | 消息分页 / 虚拟滚动、长表格懒加载、乐观更新 | 列表虚拟化 + 游标分页 |
| P2-6 一键交付 | 启动脚本（Windows/macOS）、CI、健康面板 | GitHub Actions 跑测试 + 评测门禁 |
| P2-7 桌面化（可选） | 用 Tauri 包成本地应用 | 复用现有前后端，嵌 Python sidecar |

## 三、分阶段路线图

### 阶段一：可演示打磨（约 1~2 周）

目标：让任何人在自己机器上 10 分钟内跑通完整链路，并且失败时看得懂原因。

1. 一键启动脚本（检查 Python/Node、装依赖、起前后端、打开浏览器）
2. P0-3 模型降级与中文错误提示
3. 上传/索引进度可见（可先做 SSE 推送，不做队列）
4. README 与 docs 的数字全部与最新评测对齐

**验收**：在干净机器上按文档操作，能完成"上传 → 提问 → 改表 → 确认 → 还原"全流程。

### 阶段二：单机长期可用（约 3~4 周）

目标：一个人每天用，不会因为锁、超时、额度、外部改动而出问题。

1. P0-1 长任务异步化
2. P0-2 上传安全加固
3. P0-4 并发边界（至少文档化 + 只读模式）
4. P1-3 写入冲突闭环、P1-5 可观测性

**验收**：连续使用一周无"必须重启服务"的故障；所有失败都能在界面上看到原因。

### 阶段三：团队可用（约 2~3 个月）

目标：3~10 人共享同一套语料，权限清晰、变更可追溯。

1. P2-1 身份与权限、P2-2 多租户存储
2. P1-1 评测集扩到 100+ 并接入 CI
3. P1-4 批量确认、P2-3 版本历史

**验收**：两个用户同时操作同一工作区不互相破坏；任意一次文件变更都能追溯到人与时间。

## 四、怎么衡量"改好了"

| 维度 | 指标 | 现在 | 目标 |
|---|---|---|---|
| 检索质量 | Recall@5 | 0.9286（36 题） | ≥ 0.90（100+ 题，更难的集合） |
| 拒答 | 拒答准确率 | 1.0000（8 负样本） | ≥ 0.95（30+ 负样本） |
| 回答可信度 | 引用可追溯率（回答里的数值都能在引用的片段里找到） | 未度量 | ≥ 0.98 |
| 延迟 | 首个 token / 整轮耗时 | 1~2s / 5~20s | 首个 token < 1.5s，P95 整轮 < 15s |
| 稳定性 | 需要重启才能恢复的故障 | 存在（锁、额度） | 0 次/周 |
| 成本 | 每千次问答的模型费用 | 未统计 | 可统计 + 有预算上限 |
| 安全 | 越界路径 / 未审批写入 | 0（有测试） | 保持 0，并新增注入类用例 |

**关于"引用可追溯率"**：这是一个可以自动化的指标——把回答里的数字抽出来，
检查它们是否出现在本轮引用的片段文本中。它比人工评审便宜，且能直接反映"有没有编"。

## 五、明确不做的事（以及为什么）

写清楚"不做什么"和"做什么"同样重要：

| 不做 | 原因 |
|---|---|
| GraphRAG / 知识图谱 | 语料是几十份制度与表格，实体关系简单；图谱的构建与维护成本远大于收益 |
| HyDE / 多查询扩展 | 问题以"某个事实是多少"为主，多查询提升有限而延迟翻倍 |
| 多 Agent 协作（Planner + Executor + Critic） | 单 Agent 已能覆盖；多一层角色会引入不可预测性与成本，且更难调试 |
| 自研向量库 / 自研重排 | Qdrant 与 bge 系列已经足够好且可替换 |
| 微调自己的检索模型 | 没有标注数据规模；先靠评测集把工程参数调好收益更高 |
| K8s / 服务网格 | 当前是单机单用户；上这些会让部署复杂度暴涨而无实际收益 |
| 把全部工具都暴露给模型 | 工具越多，选择准确率越低（本项目刻意只留 13 个） |

## 六、风险登记

| 风险 | 影响 | 现状对策 | 下一步 |
|---|---|---|---|
| 模型幻觉 | 给出看似合理的错误答案 | 只能依据上下文、引用纪律、阈值拒答、兜底重读 | P1-1 引用可追溯率自动度量 |
| 模型误改文件 | 数据损坏 | 审批闭环 + 写前备份 + 可还原 | P1-4 批量确认时的冲突提示 |
| 供应商限流/涨价 | 服务不可用或成本失控 | 可换 `LLM_MODEL` / `LLM_BASE_URL` | P0-3 降级链；P1-6 成本统计 |
| 语料含敏感信息 | 数据外泄 | Embedding/Rerank 本地；只有对话出网 | 提供"完全离线"配置档（本地 LLM） |
| 单机故障 | 数据丢失 | 备份目录（保留 50 份） | P2-3 版本历史 + 定期导出 |
| 依赖升级破坏行为 | 回归 | 79 + 48 项单测 + 评测脚本 | P2-6 接 CI |

## 七、如何继续推进（给接手者的建议）

1. **先跑基线**：`pytest`、`npm run check:sse`、`eval_retrieval.py --dense --rewrite`
   三条命令跑通，记住当前数字。
2. **再改一处**：从 P0 里挑一项，改完用第 1 步的命令验证是否回退。
3. **补测试**：每个 bug 都先写一个能复现的测试（本项目现有的每个失败模式都有对应测试，
   包括 SSE 的 CRLF、历史窗口、空回复）。
4. **更新数字**：改了检索或模型，必须重跑评测并把新数字写回文档——否则文档会变成谎言。

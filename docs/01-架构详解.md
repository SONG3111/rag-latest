# 01 架构详解

## 一、为什么要分层

这个项目的复杂度集中在四件事上，而且它们的失败方式完全不同：

1. **模型可能乱答**（幻觉、用过期的旧结论）
2. **模型可能乱改文件**（改错单元格、覆盖别人的数据）
3. **检索可能给错材料**（召回不准、把无关片段当答案）
4. **界面必须让人看得见过程**（正在调什么工具、改了什么、依据是什么）

如果把这些混在一个"聊天接口"里，任何一处出问题都只能整段重写。所以这里按
**能力来源**切层，而不是按"前端/后端"切：每一层可以单独测试、单独替换。

## 二、五层结构

```
┌────────────────────────────────────────────────────────────────────────┐
│ ① 表现层  Vue 3 + Vite + TypeScript + Pinia + Ant Design Vue            │
│   职责：三栏布局、SSE 消费、Diff 卡片、引用面板                          │
│   不知道：模型是谁、检索怎么做的、文件怎么写的                            │
├────────────────────────────────────────────────────────────────────────┤
│ ② 接口层  FastAPI 路由（REST + SSE）                                    │
│   职责：HTTP 契约、参数校验、把图事件翻译成 SSE 帧、持久化会话消息         │
│   不知道：工具怎么执行、检索怎么排序                                     │
├────────────────────────────────────────────────────────────────────────┤
│ ③ 编排层  LangGraph 单 Agent（agent ⇄ tools 循环 + nudge 节点）          │
│   职责：决定调哪个工具、拦住写入类工具、维护引用与提案                    │
│   不知道：Excel 单元格怎么改、向量库怎么查                               │
├────────────────────────────────────────────────────────────────────────┤
│ ④ 能力层                                                                │
│   ├─ 检索能力：改写 → 双路召回 → 去重 → RRF → 重排 → 阈值 → 父块上下文    │
│   └─ 文档能力：MCP Server（stdio 子进程）里的 13 个 Excel/Word 工具       │
│   这一层是可替换的：换成别的检索器、别的工具集，上面的层不用动            │
├────────────────────────────────────────────────────────────────────────┤
│ ⑤ 存储层                                                                │
│   ├─ SQLite：工作区、文件、分块、消息、操作审计、工具清单                 │
│   ├─ Qdrant local：每工作区一个 collection 的向量索引                    │
│   └─ 文件系统：data/workspaces/<id>/ 沙箱目录、data/backups/<id>/ 备份    │
└────────────────────────────────────────────────────────────────────────┘
```

代码位置对照：

| 层 | 目录 |
|---|---|
| ① 表现层 | `frontend/src/` |
| ② 接口层 | `backend/app/api/`、`backend/app/main.py` |
| ③ 编排层 | `backend/app/agent/` |
| ④ 能力层 | `backend/app/retrieval/`、`backend/app/mcp_client.py`、`mcp-office-server/` |
| ⑤ 存储层 | `backend/app/models.py`、`backend/app/services/`、`backend/app/retrieval/vector_store.py` |

### 分层带来的直接收益

- `mcp-office-server/` 可以**脱离本项目单独安装使用**（它不认识 FastAPI、不认识 Qdrant）。
- 检索能力有独立的评测脚本（`scripts/eval_retrieval.py`），不需要起前端。
- Agent 的控制流用**脚本化的假模型**测试（`backend/tests/test_agent.py`），
  不需要 API key 也能验证"写入是否被拦下""循环是否被切断"。

## 三、编排层：Agent 图长什么样

```
        ┌───────────────────────────────┐
        │  START                        │
        └───────────────┬───────────────┘
                        ▼
              ┌───────────────────┐
        ┌────▶│ agent 节点         │  流式调用模型（astream）
        │     │ 系统提示 + 历史     │  产出：文本 / tool_calls
        │     └─────────┬─────────┘
        │               │
        │      ┌────────┴─────────┐
        │      ▼                  ▼
        │ 有 tool_calls?     没有 tool_calls
        │      │                  │
        │      ▼                  ├─ 正文为空？───────▶ nudge（空回复纠正）
        │ ┌──────────┐            ├─ 文件变过且没读？──▶ nudge（时效性纠正）
        │ │tools 节点 │            └─ 其它 ─────────────▶ END
        │ │ 门控/执行 │
        │ └────┬─────┘
        └──────┘  回到 agent，把工具结果喂回去
```

### 状态（AgentState）

| 字段 | 作用 |
|---|---|
| `messages` | 本轮的消息序列（历史 + 新用户消息 + 工具结果） |
| `iterations` | 模型调用次数，用于切断死循环（上限 `AGENT_MAX_ITERATIONS`，默认 12） |
| `tool_calls_made` | 本轮真正执行过几次工具，决定是否触发时效性兜底 |
| `nudges` | 已经纠正过几次。两类兜底**共用这一个计数器**，因此每轮最多纠正一次，避免来回打转 |
| `citations` | 检索到的出处，最终推给前端引用面板 |
| `proposals` | 本轮产生的待确认提案 |

### 三个关键机制

**机制 1：工具门控（写入永不直通）**

```
模型说要调 update_cells
        │
        ▼
这个工具来自 MCP 吗？ ── 否 ──▶ 直接执行（例如知识库检索，本地工具）
        │ 是
        ▼
它带 readOnlyHint 吗？ ── 是 ──▶ 直接执行（读文件是安全的）
        │ 否
        ▼
不执行！先读当前值 → 生成 Diff → 落库成 proposed → 把"待确认"告诉模型
```

注意最后一行：模型收到的是 `status: pending_user_approval`，而不是执行结果。
这样模型不会以为"已经改完了"，它会在回复里请用户去确认。

**为什么不做成 MCP 内部拦截？** 见 [03 技术选型对比](03-技术选型对比.md) 的"审批放在哪一层"。
简单说：MCP Server 保持无状态、可复用；审批记录落在 SQLite，服务重启后依然可审计、可还原。

**机制 2：时效性检测（历史结论会过期）**

这是实测踩出来的问题：用户重新上传了表格，模型却照着上一轮的答案回答。
根因不是模型笨，而是**上下文里的旧答案和正确答案长得一模一样**，模型没有理由怀疑它。

现在的处理分三层：

| 层 | 做法 | 触发条件 |
|---|---|---|
| 事实层 | 比较文件 `indexed_at` / 磁盘 `mtime` 与上一条消息时间 | 每轮开头 |
| 提示层 | 注入一条系统消息，点名"哪个文件、什么时候变的、旧结论作废" | 检测到变化时 |
| 兜底层 | 模型没读文件就给出带数值的结论 → 打回重读一次 | 检测到变化 + 模型没调工具 |

三个细节值得注意：

- 时间是 **UTC 对齐**的。数据库存 UTC-naive，磁盘 mtime 必须转成 UTC 再比，
  否则本地时区会让人误判"每分钟文件都在变"。
- 用 `_recent_messages()` 取**最近 60 条**消息。一开始写成
  `ORDER BY created_at ASC LIMIT 60`，等于永远只看对话开头——长对话直接失真。
- 兜底只做一次。模型第二次仍然不读，就放行（宁可答得不完美，也不能卡住）。

**机制 3：流式与"权威文本"**

前端看到的是逐字冒出来的回答，但这里有两个坑：

1. 模型在一次工具调用前可能先输出一段"我先看看文件…"，这段文字也会被推给用户，
   而它并不是答案。
2. 推理模型偶尔只输出思考、不输出正文（LangChain 会把思考丢掉），于是整轮是空的。

解决方式：**token 事件照常流，`done` 事件由路由统一发给前端**，
内容 = 落库的那份文本。前端在 `done` 时用权威文本覆盖累积内容，
于是"看到的"和"存下来的"永远一致，空回复也会变成一句明确的提示。

## 四、能力层之一：检索管线

```
用户问题
   │
   ▼
① 查询改写（LLM，可关）      把"报销咋整"补成"员工费用报销流程"；
   │                          把"那第三条呢"补成"制度第三条规定了什么"
   ▼
② 双路召回（只对子块）
   ├─ 向量检索 Qdrant（cosine，top 20）   管语义相近、换个说法
   └─ BM25（中文分词 + bigram，top 20）   管精确 token：金额、单号、人名、条款号
   ▼
③ 跨通道去重（内容指纹：前 200 字归一化哈希）
   │   同一个片段被两路同时召回时只占一个位次
   ▼
④ RRF 融合（k=60，dense 权重 1.0 / sparse 0.8）
   │   两种分数不同量纲，只有排序可比
   ▼
⑤ 交叉编码器重排（本地 bge-reranker-v2-m3，20 个候选）
   │   逐对读 query + 片段，给出真实相关性分数
   ▼
⑥ 相关性阈值过滤（默认 0.02）
   │   低于阈值全部丢弃 → 返回空 → 模型必须回答"没有找到"
   ▼
⑦ 父块上下文附加 + 引用（文件 + 精确位置）
```

参数都在 `.env`：`RETRIEVAL_VECTOR_TOP_K=20`、`RERANK_CANDIDATES=20`、
`RERANK_TOP_N=5`、`RERANK_SCORE_THRESHOLD=0.02`。

### 为什么要有父子分块

召回要**精确**，回答要**完整**，这两件事用同一种块大小是矛盾的：

| | 子块 | 父块 |
|---|---|---|
| 粒度 | Excel 一行 / Word 一段 | 12 行一组 / 一个标题章节 |
| 用途 | 被嵌入、被 BM25 索引、被重排 | 命中后作为上下文喂给模型 |
| 引用精度 | `报销明细!第3行` | — |
| 是否入向量库 | 是 | **否**（省一半嵌入成本） |

例子：命中"金额=8600"，父块会把整行 + 表头 + 同组其它行一起给模型，
所以模型既知道这一行是什么，也知道它属于哪张表、表头是什么。

### 为什么必须有阈值

没有阈值时链路**永远**返回 top-5。用户问一个语料里根本不存在的问题（"公司班车几点发车"），
模型一样会拿到 5 段"最不无关"的文本，然后编一个像样的答案。

实测（36 题评测集，其中 8 题是语料外的负样本）：

| 配置 | Recall@5 | MRR | 拒答准确率 |
|---|---|---|---|
| 仅 BM25 | 0.8214 | 0.8036 | 0.2500 |
| + 向量 + 重排 + 阈值 | 0.8929 | 0.8571 | **1.0000** |
| + 查询改写（完整链路） | **0.9286** | **0.9107** | **1.0000** |

阈值不是抄来的，是扫出来的（`--sweep`）：0.02 是第一个把拒答做到 100% 的取值，
再往上只会损失召回。换语料或换重排模型必须重新扫——阈值取决于被打分文本的长度，
长段落上正确命中能到 0.9，而检索实际打分的短子块只有 0.05 量级。

## 五、能力层之二：MCP 文档工具

13 个工具，按注解分成两类：

| 类别 | 工具 | 审批 |
|---|---|---|
| 读取（6） | `list_files`、`get_doc_structure`、`read_range`、`read_paragraphs`、`read_table`、`find_text` | 直接执行 |
| 写入（7） | `update_cells`、`set_formula`、`insert_rows`、`delete_rows`、`format_range`、`replace_text`、`update_table_cell` | 生成提案，等确认 |

设计细节：

- **路径沙箱**：所有路径参数都是"相对于沙箱根"的，`../`、绝对路径、符号链接逃逸
  一律拒绝（实现见 `mcp-office-server/src/mcp_office_server/sandbox.py`）。
- **窗口化工作区**：沙箱根是共享的 `data/workspaces/`，Agent 侧再把路径前缀成
  `<workspace_id>/<file>`。`list_files` 的结果会被**过滤成本工作区的文件**——
  否则模型会看到别的目录、甚至界面上早已删除但磁盘还在的文件，然后去读错文件。
- **写入冲突检测**：读取时返回文件 `digest`，写入时可带上它；文件在此期间被改动过
  就报 `WriteConflict`，避免覆盖别人的修改。
- **未注册的能力**：上游实现里的图表、透视表、密码保护、批注等代码保留在包内但不注册为
  工具。工具越多，模型的工具选择准确率越低——13 个已经是刻意精简后的数量。

## 六、存储层与数据模型

```
workspaces ──1:N──▶ document_files ──1:N──▶ chunks (parent/child)
     │
     ├──1:N──▶ messages（会话记录，含 citations / proposals）
     └──1:N──▶ operations（提案与审计：状态、Diff、备份路径、结果、错误）
```

| 表 | 关键字段 | 说明 |
|---|---|---|
| `workspaces` | id, name | 一个工作区 = 一个知识库 + 一个目录 |
| `document_files` | rel_path, kind, checksum, status, chunk_count, indexed_at | 文件元数据；`indexed_at` 也用于时效性判断 |
| `chunks` | ordinal, text, location, level(parent/child), parent_id, token_counts | 分块；父块不嵌入，子块嵌入 |
| `messages` | role, content, citations, tool_calls | 会话；引用随消息一起落库，刷新页面不丢 |
| `operations` | tool_name, arguments, diff, status, backup_path, result, error | 审批闭环的全部证据 |
| `mcp_tools` | name, description, read_only, destructive | MCP 工具清单快照，供界面展示 |

### 磁盘布局

```
data/
├── app.db                      # SQLite
├── qdrant/                     # 嵌入式向量库
├── workspaces/<workspace_id>/  # 用户文件的沙箱目录（MCP 只能看到这里）
└── backups/<workspace_id>/     # 每次写入前的自动备份（保留最近 50 份）
```

### Schema 演进的坑

`Base.metadata.create_all()` **只建缺失的表，从不修改已存在的表**。所以给模型加字段后，
用全新数据库跑的测试全绿，真实数据库却在写入时报 `no such column`。
`backend/app/migrations.py` 负责启动时补列与索引，策略是**只增不删**，
因此可以每次启动自动执行。

## 七、六条设计原则

这六条是从实际 bug 里总结出来的，不是口号：

1. **失败要往安全的方向倒（fail safe）**
   - 没有注解的工具默认需要审批（未知 = 危险）
   - 检索不确定就返回空，让模型必须说"没找到"
   - 不改用户的文件，只生成提案

2. **不确定的事交给确定性代码，而不是再问一次模型**
   - 路径是否越界：代码判，不靠提示词
   - 是否过期：比时间戳，不靠模型自觉
   - 循环是否结束：`iterations` 上限，不靠模型"决定停止"
   - 提示词只用来表达**意图和风格**，不用来兜住**正确性**

3. **可观测优于聪明**
   - 工具调用、参数、结果、引用分数、Diff、备份路径全部落库
   - 界面上能看到"正在调用哪个工具"，出问题能定位到哪一步

4. **能力与策略分离**
   - MCP Server 只负责"能做什么"（无状态、可复用）
   - Agent 层负责"允许做什么"（审批、沙箱窗口、时效性）

5. **本地能做的事不出去**
   - Embedding / Rerank 用本地权重：语料原文不出机器
   - 云端只留最需要通用推理能力的对话生成

6. **一切结论都要能被脚本复现**
   - 检索效果有评测集，性能有对照实验，每个 bug 都有对应的回归测试
   - 文档里的数字都标注了复现命令

## 八、已知的架构级取舍

| 取舍 | 现在的选择 | 代价 |
|---|---|---|
| 单 Agent vs 多 Agent | 单 Agent + 工具循环 | 复杂任务不如 Planner 结构清晰，但可控、便宜、好调试 |
| 嵌入式 Qdrant vs 服务端 | 嵌入式（单进程文件锁） | 多进程同时访问会冲突（backend 与脚本不能同时跑） |
| SQLite vs Postgres | SQLite | 单机足够；多用户/并发写要换 |
| 全量重建索引 vs 增量 | 单文件重建（`/files/{id}/reindex`） | 换嵌入模型要全工作区重建（`/reindex`） |
| 同步检索 vs 后台任务 | 同步执行（SSE 阻塞等待） | 大文件上传/重建会占住请求 |

这些取舍在 [04 落地与改进](04-落地与改进.md) 里都有对应的改进计划。
